<Aside type="caution" title="Research prototype">
	k10s works end to end (a hosted node, a cluster, a bare-metal kernel) and is heavily tested, but it has not run
	in production. Read the limits below before you rely on it.
</Aside>

## What is tested

- **Isolation:** the JIT against the reference interpreter on 1,000,000 random modules, zero mismatches, on
  x86-64 and arm64; 800,000 adversarial memory programs; a red-team suite of 14 attack classes; an independent
  machine-code verifier per architecture.
- **Runtime:** unit, integration and multi-process cluster tests on both backends: node kill, graceful leave,
  restart with the same data, concurrent applies, re-apply under load with 0 failed requests.
- **Chaos:** 20 minutes on 5 nodes, 2,585 fault rounds (SIGKILL, SIGSTOP, leave and join, re-applies): 0
  invariant violations, 0 wrong bodies.
- **Abuse:** output bombs, log spam, infinite loops, crash loops, KV bombs, slowloris, hostile bundles, call
  cycles, fd exhaustion, peers that never read: a well-behaved neighbour kept 0 errors.
- **OS images:** PID 1 mode and both x86-64 disk images under QEMU on SeaBIOS and OVMF: DHCP renew, rebind and NAK,
  growth of the data partition to the disk, signed driver modules (an unsigned one is refused), state across
  reboots, reproducible builds; QEMU start to first HTTP 200 in about 0.5 s. Updates: the power cut at every step of
  an A/B update on BIOS and UEFI (always back on a good image, data kept), images that panic or never commit fall
  back, and a 20-node rollout where a bad image stops after the first wave and a good one goes through every wave.
  Secure Boot under OVMF and AAVMF with Microsoft's keys: the released image is refused, and boots with Secure Boot
  off, with own keys and with a MOK under Debian's shim; an update the firmware refuses rolls back.
  arm64: the arm64 image on AAVMF and the Raspberry Pi image behind a model of the Pi firmware (A/B through
  `autoboot.txt` and tryboot, the same power cuts; the Pi 3 on QEMU's `raspi3b` with a USB NIC), a Pi in a cluster
  with an x86-64 node, and every test suite on an arm64 host. 32-bit: the i686 image on SeaBIOS with an old CPU, an
  IDE disk and an RTL8139, the armv7 image on 32-bit ARM UEFI, the same A/B power cuts, and the test suites on i686 and
  armv7.

## Limits

| Area | Today |
|---|---|
| tenancy | one organization per node; Spectre-class side channels only partly mitigated |
| cluster identity | one shared key; no per-node identity, no signed bundles, no TLS |
| storage | key-value store durable but node-local; no replication, no consensus for singletons |
| compute | 1.1–1.6× slower than portable Go on CPU-bound code |
| ecosystem | Ten or TIR only; no Wasm or LLVM front end |
| platforms | JIT on x86-64 and arm64; other architectures on the interpreter (i686 and armv7 best effort, instances up to 256 MiB); native kernel on VM guests only; disk images for x86-64, arm64 VMs, the Raspberry Pi 3/4/5, old PCs (i686, BIOS) and 32-bit ARM VMs (signed A/B updates rolled out by the cluster), tested under QEMU, not yet on a physical machine |

## Roadmap

1. **Cluster security:** per-node identity and signed bundles, on top of today's authenticated and encrypted gossip
   and peer links.
2. **Replicated state:** a replicated key-value store per service (Raft per shard group) and leases for singletons.
3. **arm64:** the JIT runs on arm64 hosts and in the arm64 and Raspberry Pi 3/4/5 images; the native kernel's arm64
   port will reuse it. 32-bit (i686, armv7) stays on the interpreter.
4. **Native bare metal:** UEFI, ACPI, modern virtio, NVMe and a durable key-value log; then cloud NICs.
5. **Performance:** register allocation in the JIT, 32-bit TIR operations, cheaper cross-node forwarding.
6. **Ecosystem:** a Wasm → TIR translator, so Rust, C, Go and Zig can target k10s.

## Platform decisions

- **Network:** wired Ethernet only (DHCPv4 or a static address); no Wi-Fi.
- **Boot:** UEFI and legacy BIOS. Images are not signed for Secure Boot: turn it off, or sign the image with your own
  key and enroll it (sbctl, or a MOK under Debian's shim).
- **Order:** x86-64 first, then arm64 and the Raspberry Pi; i386 and armv7 are best effort, on the interpreter.
- **Updates:** OS images are signed by the k10s release key and spread over gossip like code.
- **One image:** a single installed image boots the Linux-based tier or the native kernel, chosen from the hardware
  found at boot.
