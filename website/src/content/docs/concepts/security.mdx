## Threat model

Workloads on a node belong to **one organization**: they may be buggy, they must never crash, corrupt or starve
each other or the node. Within that model k10s defends against:

- a module that reads or writes outside its slot, jumps outside its code, or calls a host function it did not
  import;
- a workload that crashes, hangs or starves the node or other workloads through host functions, ingress, the
  admin API or the peer protocol;
- a service calling a service its `calls` allowlist does not grant, or telling such a service from one that does
  not exist;
- memory-safety bugs in the runtime, the mesh or the bare-metal kernel.

Report vulnerabilities as described in [SECURITY.md](https://github.com/bzzdevlabs/k10s/blob/main/SECURITY.md).

## Layers

| Layer | What it does |
|---|---|
| **Software fault isolation** | the boundary: masked memory, structured control flow, closed host API ([details](/k10s/concepts/isolation/)) |
| **Machine-code verifier** | an independent checker re-verifies the generated code of every function in the test suites |
| **Process sandbox** | `k10s node` drops to seccomp (96 syscalls) and Landlock (data directory only) once its listeners are bound |
| **systemd hardening** | an optional unit adds its own layer ([Production setup](/k10s/guides/production/)) |

On bare metal there is no OS layer: hardware NX and W^X for kernel and JIT code are the only extra barrier, so
machine-code verification matters most there.

## Who may deploy

- **Admin API** (`/_k10s/`: apply, status, logs, cluster): every request is signed with the node's admin key
  (HMAC-SHA256 over the node process's random audience, method, target, time, nonce and the body's hash;
  `--admin-token-file`, else `DATA/admin.key` created on first start). Audience, signature, 60 s clock window and
  nonce cache are checked on the request head before any body is read: the key never travels, and a captured
  request can be neither altered nor replayed (not on that node, another node sharing the key, or after a restart). `health` is
  open; `metrics` is open on the dedicated admin listener (`--admin ADDR`) so scrapers need no secret that can
  deploy code.
- **Cluster:** a shared 32-byte key (`k10s keygen`). Gossip datagrams are sealed with XChaCha20-Poly1305 (key id
  and sender authenticated) and rejected before decoding when forged, stale (clock skew bound, default 300 s) or
  replayed. Peer links run a mutual handshake on fresh nonces, then encrypt and authenticate every record with
  ChaCha20-Poly1305 (per-direction keys, counter nonces: no injection, replay, reordering or reflection). Nothing
  is served on a link before the peer has proved it holds the key, and what an unauthenticated peer can make a
  node buffer is capped. Manifests and blobs are still checked against their SHA-256 when fetched; key material is
  wiped from memory when dropped.
- **OS images** (disk images updated by the cluster): installed only when signed (Ed25519) by the k10s release key
  built into the image or by a key pinned on the machine (`os_key`), for the machine's platform. Init verifies them
  itself; the node, which fetched them, is sandboxed and not trusted with that. Any validly signed image installs, an
  older one too: which one a cluster runs is the choice of whoever holds an admin key or the cluster key.
- **Secure Boot:** the images are not signed for it (no k10s shim signed by Microsoft). Turn it off, or have the
  firmware trust your own keys, or a MOK under Debian's Microsoft-signed shim, and sign systemd-boot and each image
  with that key, then the image with your k10s image key ([Secure Boot](/k10s/guides/bare-metal/#secure-boot)).
  Init logs the firmware's Secure Boot state; the kernel is in lockdown (integrity) either way.

### Key rotation

A node accepts a next key besides its current one (`--cluster-next-key-file`). Rotate with three rolling restarts,
one node at a time; the cluster stays whole and serving throughout:

1. every node: `--cluster-key-file old.key --cluster-next-key-file new.key`;
2. every node: `--cluster-key-file new.key --cluster-next-key-file old.key`;
3. every node: `--cluster-key-file new.key`.

`k10s status` shows the key ids (`auth`) of each node.

## CPU side channels

All instances on a node share one address space, the caches and the branch predictors: the textbook setting for
Spectre. k10s closes the cheap gaps; **one node per mutually distrustful tenant** remains the boundary for side
channels.

| Mitigation | Status |
|---|---|
| guest accesses masked by data flow (Spectre v1) | <Badge text="default" variant="success" /> |
| `br_table` as compare trees or clamped tables | <Badge text="default" variant="success" /> |
| branch-free clamps of every guest pointer, length and offset in host code | <Badge text="default" variant="success" /> |
| coarse guest clock: 100 µs steps with randomized edges (`--timer-res-us`) | <Badge text="default" variant="success" /> |
| retpolines or `lfence` on JIT indirect branches (`--jit-indirect`) | <Badge text="opt-in" variant="caution" /> |
| the runtime's own indirect branches, return-stack speculation, Spectre v4, shared caches, SMT | <Badge text="not mitigated" variant="danger" /> |

## Denial of service

| Resource | Bound |
|---|---|
| memory | one reserved instance per service, a shared burst pool, `max_instances`, KV quota per service (`--kv-max`, 256 MiB) |
| CPU | 2 ms slices, per-request `cpu_ms` budget, crash-loop backoff |
| connections | node-wide buffer budget (`--conn-buffer-max`), head and body limits, slowloris timeouts |
| calls | depth 32, 10,000 per invocation, 5 s default deadline, queue of 10,000 |
| peers | read and write caps per link; a peer that stops reading is cut off |

The shared pool, the connection budget and CPU are first come, first served between services: there is no
per-service weight yet.

## Known gaps

<Aside type="caution" title="Open items">
	- **Every key holder is fully trusted.** A node with the cluster key can deploy and read the traffic it carries.
	  No per-node identity, no revocation (rotate the key on every node), no forward secrecy.
	- **Bundles are not signed.** Whoever holds an admin key or the cluster key deploys code.
	- **No TLS** on the admin API or service ingress: signed requests cannot be forged or replayed, but bundles,
	  status and logs travel in clear; keep the admin listener on a trusted network or behind a TLS proxy.
	- **Traffic analysis:** message sizes and timing are visible.
</Aside>
