With isolation done by the compiler, a node needs from the OS only memory, a timer, a NIC and a console. So the same
runtime also boots **as its own kernel**: `k10-metal`. No processes, no system calls, no user/kernel boundary, no
per-workload page tables: one identity-mapped address space over all of RAM on up to 64 cores, polling virtio queues
directly. It finds the machine in the ACPI tables (no AML interpreter) and powers off and reboots through ACPI. It
boots on QEMU (`pc`, `q35`, `microvm`; KVM or TCG), Firecracker and Cloud Hypervisor. In a cloud, where every node
is already a VM, this deletes the guest Linux.

| | k10-metal | Linux guest, same QEMU setup |
|---|---|---|
| image | 1 MB, JIT, cluster layer, ACPI and virtio included | 8.2 MB kernel + 0.9 MB initramfs |
| kernel entry → ready | about 3 ms | about 1.25 s |
| QEMU start → first HTTP 200 | median 96 ms | 1,437 ms |
| smallest `-m` that serves under load | 3 MiB | 88 MiB |

## Boot it

<Steps>

1. Build the kernel and a bundle of test services (from `metal/`):

   ```bash
   ./build.sh
   ```

2. Boot it in QEMU/KVM with an admin key. The serial console is on stdout; host port 8090 forwards to the guest's
   port 80. The key reaches the guest as a QEMU fw_cfg file, never on the kernel command line.

   ```bash
   k10s keygen -o admin.key
   ADMIN_KEY=admin.key APPEND="k10.verbose" ./run.sh
   ```

   <Terminal
   	variant="qemu"
   	title="QEMU — k10-metal (serial)"
   	cwd="~/k10s/metal"
   	session={`
   «teal:k10-metal ready 4.38ms» vm->kmain=53.7ms svc=19 src=initrd engine=jit cpus=1 used=836K img=708K ram=65023K
   [log] hello from the log service
   apply: manifest v2: 2 service(s), 2 here: echo, hello
   `}
   />

3. Call it like any node:

   ```bash
   curl localhost:8090/hello/
   curl 'localhost:8090/sha/?n=1000'
   k10s status --node 127.0.0.1:8090 --admin-token-file admin.key
   export K10S_ADMIN_TOKEN_FILE=admin.key   # tools/admin_auth.py signs requests for curl
   curl -H "Authorization: $(tools/admin_auth.py localhost:8090 POST /_k10s/apply @out/bundle.k10b)" \
     --data-binary @out/bundle.k10b localhost:8090/_k10s/apply
   ```

   Admin requests are signed as on hosted nodes (for the guest's `/_k10s/audience`, new at every boot);
   `/_k10s/health` and `/_k10s/audience` are open. Without an admin key the guest serves
   only `health` of its admin API.

</Steps>

`SMP=4 ./run.sh` boots four CPUs: CPU 0 runs the network, CPU-heavy requests are spread over all four.
`PLATFORM=q35 ./run.sh` (or `pc-legacy`, `pc-modern`, `microvm`, `microvm-v2`) picks another machine and NIC;
`DISK=disk.img` adds a virtio-blk disk. `./test.sh` runs the in-kernel self tests and the end-to-end checks on every
platform, `./vmm-test.sh` the same kernel on Firecracker and Cloud Hypervisor.

A signed `POST /_k10s/power` with the body `off` or `reboot` powers the guest off or reboots it through ACPI, after
it has left its cluster:

```bash
curl -H "Authorization: $(tools/admin_auth.py localhost:8090 POST /_k10s/power off)" --data-binary off \
  localhost:8090/_k10s/power
```

## Join a cluster

The guest is a full cluster member next to Linux-hosted nodes: gossip membership, desired state fetched from
peers, the same placement, forwarding both ways.

The guest sits behind QEMU's user networking, so its gossip, peer and HTTP ports are forwarded to the host and it
advertises those host addresses. Two hosted nodes and one guest:

```bash
k10s keygen -o cluster.key
k10s keygen -o admin.key
k10s node --http 127.0.0.1:19001 --gossip 127.0.0.1:19101 --rpc 127.0.0.1:19201 --mem 64MiB --cluster-key-file cluster.key --admin-token-file admin.key &
k10s node --http 127.0.0.1:19002 --gossip 127.0.0.1:19102 --rpc 127.0.0.1:19202 --mem 64MiB --cluster-key-file cluster.key --admin-token-file admin.key --join 127.0.0.1:19101 &
qemu-system-x86_64 … \
  -netdev user,id=n0,hostfwd=tcp:127.0.0.1:19003-:80,hostfwd=udp:127.0.0.1:19103-:7946,hostfwd=tcp:127.0.0.1:19203-:7947 \
  -fw_cfg name=opt/k10s/cluster_key,file=cluster.key -fw_cfg name=opt/k10s/admin_key,file=admin.key \
  -append "k10.join=127.0.0.1:19101 k10.gossip=127.0.0.1:19103 k10.rpc=127.0.0.1:19203 k10.http=127.0.0.1:19003 k10.mem=67108864"
curl -H "Authorization: $(K10S_ADMIN_TOKEN_FILE=admin.key tools/admin_auth.py localhost:19001 POST /_k10s/apply @out/bundle.k10b)" \
  --data-binary @out/bundle.k10b localhost:19001/_k10s/apply
```

`./cluster-test.sh` runs two hosted nodes and one guest through join, apply, routing, failover and rejoin, key
rotation, a node with the wrong key and a flood of unauthenticated links. Peer links use the same `secure::Link`
code as hosted nodes; at most 16 accepted links may be in their handshake on a guest.

## Secrets (fw_cfg)

| fw_cfg file | Meaning |
|---|---|
| `opt/k10s/admin_key` | admin key (`k10s keygen`); requests to `/_k10s/*` but `health` must be signed with it; without it only `health` is served |
| `opt/k10s/cluster_key` | the cluster key, the same as the hosted nodes' (or boot with `k10.insecure_unauthenticated_cluster`) |
| `opt/k10s/cluster_next_key` | next cluster key during a rotation ([Security](/k10s/concepts/security/#key-rotation)) |

Pass each with `-fw_cfg name=opt/k10s/<name>,file=FILE` (`run.sh`: `ADMIN_KEY=`, `CLUSTER_KEY=`,
`CLUSTER_NEXT_KEY=`). A malformed key stops the boot, and so does a cluster key without RDRAND (link nonces come
from it; a failed RDRAND fails the link).

## Kernel command line

| Option | Meaning |
|---|---|
| `k10.verbose` | boot banner, ACPI summary, phases, apply log (serial output costs about 15 µs per byte) |
| `k10.ip=A.B.C.D/P[,GATEWAY]` | static IPv4 address (default: DHCPv4, `k10.ip=dhcp`) |
| `k10.console=com1…com4\|io:0xPORT\|mmio:0xADDR\|mmio32:0xADDR\|none` | console UART (default: the ACPI SPCR table's, else COM1) |
| `k10.panic=N` | seconds before a fatal error reboots (default 10; 0 = halt) |
| `k10.apic=xapic` | keep the local APIC in xAPIC mode (unless the firmware handed over in x2APIC mode) |
| `k10.pci=full` | probe every PCI bus of the ECAM windows under a hypervisor too |
| `virtio_mmio.device=SIZE@BASE:IRQ` | a virtio-mmio slot (Linux syntax; slots in the ACPI DSDT are found anyway) |
| `k10.engine=jit\|interp` | execution engine (default `jit`) |
| `k10.smp=N` | use at most N CPUs |
| `k10.spin_us=N` | busy-poll window before halting (default 50) |
| `k10.jit_indirect=jump\|lfence\|retpoline` | Spectre v2 hardening of JIT indirect branches |
| `k10.timer_res_us=N` | guest clock resolution (default 100; 0 = full; any other value needs RDRAND) |
| `k10.join=HOST:PORT,…` | cluster seeds; with `k10.gossip=`, `k10.rpc=`, `k10.http=` (advertised addresses, default the interface's address). `k10.join`, `k10.gossip` or `k10.cluster` turns cluster mode on |
| `k10.insecure_unauthenticated_cluster` | cluster mode without a key (isolated test networks only) |
| `k10.gossip_max_skew_s=N` | clock skew allowed on gossip, seconds (default 300, at least 1) |
| `k10.node_id=HEX`, `k10.probe_ms=N`, `k10.suspicion_mult=N`, `k10.mem=BYTES`, `k10.host_alias=IP` | identity and tuning (`k10.host_alias`: the address through which the guest reaches host loopback addresses, default `10.0.2.2`) |
| `k10.selftest`, `k10.exit_on_ready` | test modes (both end in an ACPI power off) |

An invalid `k10.engine`, `k10.smp`, `k10.spin_us`, `k10.jit_indirect`, `k10.timer_res_us`, `k10.ip`, `k10.console`,
`k10.panic` or `k10.gossip_max_skew_s` value stops the boot (and reboots after `k10.panic` seconds).

The bundle comes from QEMU's `-initrd` (or `/k10s/bundle.k10b` on a disk image's boot partition), else from a bundle
baked in at build time (`EMBED=1`); with neither, the node starts empty and waits for `POST /_k10s/apply`.

## Inside

- **Boot:** PVH entry (QEMU `-kernel`, Firecracker, Cloud Hypervisor), long mode, SSE for JIT code. From the x86-64
  disk images: k10boot, its UEFI loader, which verifies the kernel's signature, or GRUB through the kernel's
  Multiboot2 entry on BIOS ([below](#choosing-the-tier)).
- **Platform:** ACPI tables without AML — CPUs, I/O APICs and overrides (MADT), power and reset registers (FADT),
  `\_S5` and virtio-mmio slots by a DSDT scan, ECAM windows (MCFG), the HPET, the console UART (SPCR); an MP table
  where there is no ACPI. x2APIC (or xAPIC), CPUs started one by one from the MADT, never by broadcast.
- **Memory:** every byte of RAM identity-mapped, above 4 GiB too; device ranges uncached; a tagged frame allocator
  shared by the heap and the instance slots; NX everywhere, the kernel and JIT code W^X, page 0 unmapped.
- **Time:** kvmclock, else the TSC calibrated against the HPET, the ACPI PM timer or the PIT; a tickless one-shot
  LAPIC timer armed only for the next deadline; an idle node takes no timer interrupts. The wall clock (gossip and
  admin request time windows) is re-read from kvmclock every 10 s.
- **Devices:** PCI through ECAM with 64-bit BARs and MSI-X; virtio-net and virtio-blk over PCI (virtio 1.x and
  legacy) and MMIO, behind `NetDevice`/`BlockDevice` traits with DMA from slot-like regions; fixed buffers
  (nothing allocated per packet), smoltcp for TCP/IP with DHCPv4, the same HTTP/1.1 ingress and host API as the
  hosted node.
- **Power:** ACPI S5 power off, the FADT reset register (then the 8042, port 0xCF9, a triple fault) for reboots;
  fatal errors reboot after `k10.panic` seconds.

<Aside type="caution" title="Limits">
	virtio only (physical NICs and disks come next); the disk is not used for storage yet, so the key-value store is
	in memory. IPv4 only, no TLS. ACPI events (the power button) are not handled and no AML method runs. Tested on
	QEMU (PVH, and the x86-64 disk images through UEFI or BIOS), Firecracker and Cloud Hypervisor only, not yet on a
	physical machine. There is no OS layer under the kernel, so the independent
	verification of the JIT's output matters most here. Full list:
	[metal/README.md](https://github.com/bzzdevlabs/k10s/blob/main/metal/README.md).
</Aside>

## On a Linux kernel (PID 1 mode)

Where k10-metal has no driver yet, Linux can be the driver layer and `k10s` the only program of the image: no shell,
no udev, no systemd. Started by the kernel as `/init`, k10s loads drivers by modalias, reads `k10s.conf` from a
`K10S-BOOT` partition, mounts `K10S-DATA` for its state (grown to the end of the disk on first boot), runs DHCP and
SNTP, and starts the node as a sandboxed child (its own user, no capabilities, Landlock, seccomp), restarting it if it
exits. The power button drains the node and powers off.
[docs/OS.md](https://github.com/bzzdevlabs/k10s/blob/main/docs/OS.md) has the boot sequence, the image layout and
every key.

Each release publishes six disk images. The x86-64 ones boot on BIOS and on UEFI (with Secure Boot on, see
[Secure Boot](#secure-boot)); the node runs services on the JIT on x86-64 and arm64, and on the interpreter on the
best-effort 32-bit images:

| Image | For | Kernel | Size |
|---|---|---|---|
| `k10s-os-V-x86_64-vm.img.xz` | QEMU/KVM guests and clouds | every driver built in, console on serial; and the native kernel | 4.8 MB |
| `k10s-os-V-x86_64-metal.img.xz` | PCs, mini-PCs, servers | signed driver modules (Intel, Realtek, Broadcom, Aquantia, USB Ethernet…), NIC firmware, console on the screen; and the native kernel | 7.2 MB |
| `k10s-os-V-aarch64-vm.img.xz` | QEMU virt (UEFI) and arm64 cloud guests | every driver built in, console on serial | 4.0 MB |
| `k10s-os-V-aarch64-pi.img.xz` | Raspberry Pi 3 B and 3 B+, 4 B, 400, CM4 and Pi 5 (SD card, USB or NVMe) | one arm64 kernel with mainline devicetrees, console on the serial pins (Pi 3, Pi 4) or debug UART (Pi 5) | 5.3 MB |
| `k10s-os-V-i686-metal.img.xz` | old PCs, BIOS only: a CPU with PAE and SSE2 (Pentium 4, Pentium M, Core, Atom, Athlon 64 and later); best effort | 32-bit kernel, IDE/SATA built in, signed NIC modules (Realtek, Intel, Broadcom, VIA, SiS, nForce, 3Com…), NIC firmware, console on the screen | 5.7 MB |
| `k10s-os-V-armv7-vm.img.xz` | QEMU virt and other 32-bit ARM UEFI machines with virtio; best effort | every driver built in, console on serial | 3.5 MB |

<Steps>

1. Download an image and write it to the machine's disk (or a USB stick it boots from); every byte of that disk is
   replaced:

   ```bash
   gh release download --repo bzzdevlabs/k10s --pattern 'k10s-os-*-x86_64-metal.img.xz' --pattern SHA256SUMS
   sha256sum -c SHA256SUMS --ignore-missing
   xz -dc k10s-os-*-x86_64-metal.img.xz | sudo dd of=/dev/sdX bs=4M conv=fsync
   ```

2. Give the node your admin key: the image has no shell to read a generated one. Mount the disk's `K10S-BOOT`
   partition (FAT, readable on any PC), copy the key and set it in `k10s.conf`:

   ```bash
   k10s keygen -o admin.key
   cp admin.key /media/K10S-BOOT/
   printf 'admin-token-file=/boot/admin.key\n' >> /media/K10S-BOOT/k10s.conf
   ```

3. Boot the machine (Secure Boot off, or [signed for it](#secure-boot)) and deploy to the address it shows on screen:

   ```bash
   k10s apply examples/app.k10s --node 192.168.1.50:80 --admin-token-file admin.key
   curl http://192.168.1.50/hello/
   ```

</Steps>

On a Raspberry Pi, write `k10s-os-V-aarch64-pi.img.xz` to the SD card (or a USB or NVMe drive the Pi boots from),
then do steps 2 and 3: `K10S-BOOT` is its first partition. A Pi 4 needs a bootloader EEPROM from 2021 or later
(any Pi 4 updated since; the Pi 5 always has one) for the image's A/B boot (`autoboot.txt`); a Pi 3 boots it with
the `bootcode.bin` on `K10S-BOOT`, its Ethernet (USB, behind the SoC's USB controller) coming up a few seconds after
the kernel. An old PC boots `k10s-os-V-i686-metal.img.xz` from its BIOS like any disk: write it to an IDE/SATA disk or
a USB stick the BIOS boots from.

The `vm` image runs the same way in QEMU, on BIOS or with OVMF for UEFI:

```bash
xz -dc k10s-os-*-x86_64-vm.img.xz > k10s.img && truncate -s 8G k10s.img
qemu-system-x86_64 -accel kvm -m 512M -nodefaults -display none -serial stdio \
  -drive file=k10s.img,if=virtio,format=raw -device virtio-rng-pci \
  -netdev user,id=n0,hostfwd=tcp:127.0.0.1:8080-:80 -device virtio-net-pci,netdev=n0
```

and the arm64 one with AAVMF (Debian's `qemu-efi-aarch64`):

```bash
xz -dc k10s-os-*-aarch64-vm.img.xz > k10s.img && truncate -s 8G k10s.img
cp /usr/share/AAVMF/AAVMF_VARS.fd vars.fd
qemu-system-aarch64 -M virt -cpu max -m 512M -nodefaults -display none -serial stdio \
  -drive if=pflash,format=raw,readonly=on,file=/usr/share/AAVMF/AAVMF_CODE.fd -drive if=pflash,format=raw,file=vars.fd \
  -drive file=k10s.img,if=virtio,format=raw -device virtio-rng-pci \
  -netdev user,id=n0,hostfwd=tcp:127.0.0.1:8080-:80 -device virtio-net-pci,netdev=n0
```

and the armv7 one with AAVMF32 (Debian's `qemu-efi-arm`): `qemu-system-arm -M virt,highmem=off -cpu cortex-a15`, the
same disk and network, and `/usr/share/AAVMF/AAVMF32_CODE.fd` and `AAVMF32_VARS.fd`.

`k10s.conf` holds `KEY=VALUE` lines: init's keys (`ip=10.0.0.5/24,10.0.0.1`, `watchdog=1`, `grow=0`) and every
`k10s node` flag (`join=10.0.0.2`, `cluster-key-file=/boot/cluster.key`).

### Choosing the tier

The x86-64 images boot either the Linux-based tier (as shipped) or the native kernel. `/k10s/tier` on `K10S-BOOT`
picks: change its `tier=linux` line to `tier=metal` (the native kernel, on UEFI and on BIOS) or `tier=auto` (UEFI:
the native kernel when it drives one of the machine's network adapters, else Linux). Both tiers read the same
`k10s.conf` and key files and join the same clusters. On UEFI the image's loader, k10boot, verifies the native
kernel's signature and counts its boots: a kernel that fails to get healthy twice in a row hands the machine back to
the Linux tier until you write `/k10s/tier` again. Until the native kernel has a disk driver its key-value store is
in memory; a node keeps its Linux-tier state on `K10S-DATA` and finds it again when switched back.
[docs/OS.md](https://github.com/bzzdevlabs/k10s/blob/main/docs/OS.md#tiers) has the details.

### Updating the image

The cluster updates its own machines. Name the new release's images in the desired state, one per platform, and
apply it to any node:

```
os {
    images = ["k10s-os-0.1.1-x86_64-metal.efi", "k10s-os-0.1.1-aarch64-pi.fat"]
    wave = 1    # nodes in the first wave; each next wave is twice as large
}
```

```bash
gh release download --repo bzzdevlabs/k10s v0.1.1 --pattern 'k10s-os-*.efi' --pattern 'k10s-os-*.fat'
k10s apply app.k10s --node 192.168.1.50:80 --admin-token-file admin.key
k10s status --node 192.168.1.50:80 --admin-token-file admin.key    # each member's image, the update step
```

The `.efi` files (and the Pi's `.fat` boot slot) are signed with the k10s release key, which every image trusts.
Nodes fetch them from each other and update in waves (1 node, then 2, 4, …): a node writes the new image to its
second boot slot, reboots into it for a trial (on a Pi through the firmware's one-shot tryboot), and keeps it once it
is back in the cluster and serves (`os-commit-grace`, 30 s). A trial that crashes
or hangs falls back to the previous slot after 3 boots, one that does not commit within `os_trial` (600 s) is
abandoned; the image is then recorded as failed and the rollout stops until you apply another one. A power cut at
any point boots a complete image. Images you build yourself install when you sign them (`k10s keygen -o key`,
`k10s image sign --key key --arch x86_64 --profile metal --version V in.efi out.efi`) and pin the key on every
machine (`os_key=` and the output of `k10s image pubkey key` in `k10s.conf`). Updates need cluster mode
(`cluster-key-file=/boot/cluster.key`, and `join=` on all but the first machine);
[docs/OS.md](https://github.com/bzzdevlabs/k10s/blob/main/docs/OS.md#updates) has the details. The kernel command line of the images is
fixed; `os/images.sh` and `os/mkimage.py` build images with your own command line, kernel or k10s binary, and
`os/kbuild.sh`, `os/mkinitramfs.py` a kernel plus initramfs for `-kernel` boots. A distribution kernel works too,
with its modules in the initramfs: `os/debian-kernel.sh` and `os/test.sh` show how for Debian 13's.

### Secure Boot

The images are not signed for Secure Boot, so firmware with Secure Boot on refuses them. BIOS boots (the i686 image)
and the Raspberry Pi are not concerned. Turn Secure Boot off in the firmware setup, or make the machine trust a key of yours:

- **Own keys** ([sbctl](https://github.com/Foxboron/sbctl)): `sbctl create-keys`, then from a live Linux system on the
  machine, with the firmware in setup mode (Secure Boot keys cleared in its setup), `sbctl enroll-keys --microsoft`
  (keep Microsoft's keys: graphics and network cards' firmware drivers are signed with them). Sign systemd-boot on
  `K10S-BOOT` once: `sbctl sign /media/K10S-BOOT/EFI/BOOT/BOOTX64.EFI`.
- **A MOK under Debian's shim**, for machines whose keys stay as they are: the shim (Debian's `shim-signed`, signed by
  Microsoft) becomes `EFI/BOOT/BOOTX64.EFI` and systemd-boot, signed with your MOK, `EFI/BOOT/grubx64.efi`;
  MokManager enrolls the MOK at the first boot ("Enroll key from disk").

Either way every image, the first one and each update, is signed twice: for Secure Boot with your key, then for k10s
with an image key of yours, pinned with `os_key` (the release key's signature does not cover yours):

```bash
k10s image payload k10s-os-V-x86_64-metal.efi uki.efi        # the UKI without the release signature
sbctl sign uki.efi                                           # or sbsign with the MOK
k10s image sign --key os.key --arch x86_64 --profile metal --version V uki.efi k10s-os-V-x86_64-metal.sb.efi
cp k10s-os-V-x86_64-metal.sb.efi /media/K10S-BOOT/EFI/Linux/k10s-a.efi   # a new machine's slot A
echo "os_key=$(k10s image pubkey os.key)" >> /media/K10S-BOOT/k10s.conf
```

Updates then name the `.sb.efi` files. An image the firmware refuses fails its 3 trial boots (systemd-boot reboots
after each refusal) and the rollout stops on it.
[docs/OS.md](https://github.com/bzzdevlabs/k10s/blob/main/docs/OS.md#secure-boot) has every step, the shim's file
layout and what to expect from real firmware (Microsoft's 2011 and 2023 CAs, SBAT revocations).

<Aside type="caution" title="PID 1 mode limits">
	Secure Boot needs your own keys or a MOK (above). i686 and armv7 nodes run on the interpreter (instances up to
	256 MiB). The Pi image is tested under QEMU behind a model of the Pi firmware (A/B through
	`autoboot.txt` and tryboot, power cuts during updates, a Pi in a cluster with an x86-64 node; the Pi 3 on QEMU's
	`raspi3b` with a USB NIC), the x86-64 images under QEMU (SeaBIOS, OVMF, NVMe, e1000e, Intel TCO watchdog, power
	cuts during updates, a 20-node rollout, Secure Boot with Microsoft's keys), the i686 image on SeaBIOS with an Atom
	N270, an IDE disk and an RTL8139, the armv7 one on AAVMF32; none yet on a physical machine.
</Aside>
