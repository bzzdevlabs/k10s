## Notes (reliability campaign)
- Leak verdict: no unbounded growth. fds, threads, VMAs, executable (JIT) mappings and fibers are flat; KV log is
  bounded by compaction; RSS ramps during warm-up then plateaus (single node: 102.2-102.6 MiB from t=5 min to 30 min;
  cluster node n0: 7.2 -> 8.0 MiB over the last 20 min, a slight drift worth a multi-hour run).
- The ~19% load errors are NOT node faults. A Python keep-alive client against the same manifest/re-apply pattern
  sees ~0 errors. Causes, found by this campaign (later harness runs report errors by kind):
  1. examples/todo.ten and counter.ten do read-modify-write on KV ("next", "index", "counter") and run up to
     max_instances (64) instances concurrently: lost updates (16k concurrent creates -> 89 duplicate todo ids;
     16k counter increments -> 18 lost). Over 30 min todo's "index" accumulates duplicate/stale ids until its
     1 MiB instance heap is exhausted and it traps (then crash-loop 503) on every POST (= 1/5 of this load).
  2. examples/chain.ten, compute.ten, nbody.ten allocate per request (read_config / query_int) without
     heap_reset(): a long-lived instance traps Unreachable every ~4k requests (the node replaces it; that one
     request gets 500). Fix: heap_reset() at the top of handle(), as todo/sort do.
